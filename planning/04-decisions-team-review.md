# ColorSense 설계 전 확정 사항 8가지 — Mateus 제안 및 역할별 의견 정리

작성: 2026-09-14 · 전제: 1차 런칭 = 기상청 API 제공 범위(한국), 데이터 소스 = 무료 범위(기상청 계열 + **Open-Meteo 무료 티어**) · 이 문서는 각 역할의 책임 범위에서 예상되는 입장·리스크·부작용을 정리한 검토용 초안이며, 최종 확정은 Mateus가 각 담당과 확인한 뒤 갱신한다.

## 데이터 소스 확장이 바꾸는 전제

Open-Meteo 무료 티어를 포함하면 프로토의 데이터 경로(WMO 코드·해양·대기질·역지오코딩)를 그대로 살릴 수 있고 해외 도시도 즉시 가능해진다. 대신 두 가지가 따라온다. 첫째, 무료 티어는 **비상업 전용**이므로 앱은 비상업(광고·유료·회사 서비스 없음)이어야 한다 — 이 조건은 아래 안건 1의 결론을 사실상 정한다. 둘째, 무료 티어는 키가 없어 서버 IP 단위로 일 10,000건·시간 5,000건·분 600건이 적용되고, 변수 10개 초과 요청은 가중 계산된다. 따라서 "기상청 = 한국 정밀, Open-Meteo = 해외 + 한국 보조/폴백"의 **이중 소스 구조**가 기본 아키텍처가 된다.

---

## 안건 1. 상업 여부

**Mateus 제안** — Open-Meteo 무료 티어를 쓰기로 했으므로 1차는 비상업으로 확정하고, 광고·유료 전환 시점에 데이터 소스 계약을 다시 검토하는 조건을 로드맵에 남긴다.

**Theo(백엔드)** — 비상업이면 BFF에서 Open-Meteo를 키 없이 호출해도 약관 문제가 없다. 다만 앱스토어 등록 자체가 상업으로 해석될 여지는 없는지 약관 원문을 확인해 두고, 나중에 상업 전환 시 Open-Meteo Standard(€29/월)로 갈아타는 경로를 어댑터 한 겹으로 열어 두겠다.
**Mark(인프라)** — 비상업이라도 인프라 비용은 발생한다. BFF·캐시·스케줄러를 AWS 프리티어 범위(Lambda + DynamoDB/ElastiCache 소규모)로 맞추면 월 비용을 거의 0에 가깝게 유지할 수 있다.
**Cecilia(디자인)** — 비상업이면 광고 영역을 설계에서 제외할 수 있어 배경색 중심의 화면이 온전히 살아난다. 출처 표기(기상청·Open-Meteo)만 확보하면 된다.
**Joy(QA)** — 배포 채널(TestFlight/내부 배포 vs 스토어 공개)이 정해져야 호환성 테스트 대상 기기·OS 범위를 잡을 수 있다.

**잠정 결론** — 1차 비상업, 스토어 공개 여부는 Mateus가 별도 결정. 상업 전환 시 데이터 계약 재검토를 로드맵 조건으로 기록.

## 안건 2. 도시 목록과 대표 지점 카탈로그

**Mateus 제안** — 한국은 특별시·광역시·특별자치시도 + 도청 소재지 + 인구 상위 도시로 약 30~50개, 해외는 나라별 수도 + 1~2개 대도시로 시작하되 1차 노출 국가는 소수(예: 한국인 방문 상위 10~20개국)로 제한한다. 대표 지점은 시청(구청) 좌표.

**Theo** — 카탈로그는 정적 JSON/DB 테이블로 백엔드가 소유한다. 한국 도시는 nx/ny 격자, 중기예보 육상·기온 regId, 에어코리아 측정소, 해안 여부, 한/영 표기를 필드로 갖고, 해외 도시는 위경도·타임존·한/영 표기·해안 여부를 갖는다. 외부 역지오코딩(BigDataCloud)과 IP 위치 API는 제거하고 "GPS → 카탈로그 최근접 도시"로 대체한다.
**Lisiena(프론트)** — 검색은 카탈로그 내 한/영 문자열 매칭으로 충분하다. 도시 수가 수백 개면 클라이언트에 카탈로그를 내려받아 오프라인 검색도 가능하다.
**Lily(앱)** — 앱은 카탈로그를 번들에 포함하고 버전을 두어 갱신하면 첫 실행에 네트워크 없이 도시 선택이 가능하다. 카탈로그 버전 필드를 API에 넣어 달라.
**Cecilia** — 도시명 표기 규칙(한글 자간, 영문 대문자 여부, 국가명 병기)을 카탈로그 단계에서 통일해야 한다. "서울 · 대한민국"인지 "SEOUL / KOREA"인지.
**Joy** — 격자 좌표 오기입이 가장 흔한 결함이다. 카탈로그 각 행에 대해 API 응답이 오는지 자동 검증하는 스모크 테스트를 만들겠다.

**잠정 결론** — 카탈로그는 Theo 소유의 버전 관리 데이터, 한국 30~50개 + 해외 소수 국가로 시작, 외부 지오코딩 제거.

## 안건 3. 쿼터 예산과 캐시 정책

**Mateus 제안** — 클라이언트는 절대 외부 API를 직접 호출하지 않는다. BFF가 발표 시각 기준으로 수집·캐시하고, 앱은 BFF만 본다.

**Theo** — 기상청 공공데이터포털 일 10,000건, API허브 일 20,000건. 한국 50개 도시 × (실황 24 + 초단기 24 + 단기 8 + 중기 2) = 2,900건/일로 여유 있다. Open-Meteo는 일 10,000건 제한이지만 변수 14개 요청이 약 1.4건으로 계산되므로 해외 도시를 100개까지 늘려도 15분 주기(96회/일 × 1.4 × 100 = 13,440건)는 초과한다. 해외는 30분 주기 또는 "최근 24시간 내 조회된 도시만 갱신"하는 수요 기반 캐시로 가야 한다. 대기질·해양은 1시간 주기.
**Mark** — 스케줄러는 EventBridge + Lambda, 캐시는 DynamoDB(TTL) 정도면 프리티어 안에 든다. 쿼터 소진 80%에서 알림, 100%에서 수집 중단 로직을 넣겠다. Open-Meteo는 IP 단위 제한이므로 NAT 게이트웨이 IP가 바뀌지 않도록 고정한다.
**Lisiena** — 앱 쪽은 BFF 응답에 `updatedAt`과 `nextUpdateAt`을 받아 그 사이엔 재요청하지 않도록 한다. 프로토처럼 한 번 불러오고 끝나는 구조는 폐기.
**Joy** — 쿼터 소진 상황을 재현할 방법(BFF에 강제 소진 플래그)이 있어야 테스트가 된다.

**잠정 결론** — BFF 필수, 한국은 발표 시각 스케줄, 해외는 수요 기반 캐시, `updatedAt/nextUpdateAt` 계약 필수.

## 안건 4. 1차 범위에 넣을 데이터 항목

**Mateus 제안** — 1차 필수: 현재 온도·체감·날씨 상태·시간별 24시간·일별 7일·습도·풍속풍향·강수확률·일출일몰·미세먼지/황사. 2차: 파도, 자외선, 기상특보 푸시.

**Theo** — 한국에서 위 필수 항목은 기상청 실황+단기+중기와 에어코리아, 천문연 출몰 API 4종으로 커버된다. 파도는 기상청 해양 부이가 지점 기반이라 도시 매핑이 애매하니 2차가 맞다. 해외 도시는 Open-Meteo 한 곳에서 필수 항목이 다 나오지만 미세먼지는 CAMS 모델값이라 한국 실측(에어코리아)과 기준이 다르다 — 화면에서 "예측값" 표기가 필요하다.
**Cecilia** — 항목이 정해지면 상세 시트 레이아웃(4타일 + 주간)을 시간별 스트립 포함 구조로 다시 그린다. 항목 수가 늘면 배경색 중심의 여백이 죽으니 1차 항목을 더 줄이는 것도 고려해 달라(예: 강수확률·습도는 시트 안으로).
**Lily** — 위젯(홈 화면)을 1차에 넣을지 결정이 필요하다. 위젯은 백그라운드 갱신 정책과 배터리에 직결된다.
**Joy** — 항목마다 "값 없음" 상태가 정의돼야 한다(내륙 파도 N/A, 해외 대기질 예측값, 야간 자외선 등).

**잠정 결론** — Mateus 제안대로 1차 항목 확정, 위젯은 2차, 해외 대기질은 "예측값" 표기, 항목별 결측 상태 정의를 기획 산출물에 포함.

## 안건 5. 날씨 코드 체계 통합 — 컬러 엔진 입력 재정의

**Mateus 제안** — BFF가 기상청(SKY/PTY/PCP/시정/특보)과 Open-Meteo(WMO 코드)를 모두 **내부 공통 모델** `{sky 0~3, precip, inten, fog, storm, dust}` — 즉 프로토의 `decode2` 출력 형태 — 로 정규화해 내려준다. 컬러 엔진과 라벨은 이 모델만 본다.

**Theo** — 매핑 규칙: SKY 1→sky0, 3→sky2, 4→sky3(기상청엔 "대체로 맑음" 단계가 없어 sky1은 Open-Meteo에서만 발생). PTY 1/5→rain, 2/6→sleet, 3/7→snow, 4→showers(sky2 + rain). 강도는 PCP/SNO 값 구간으로 1~3. 뇌우는 낙뢰 특보 또는 실황 LGT, 안개는 시정 관측(1km 미만) 또는 안개 특보, dust는 에어코리아 PM10 등급 + 기상청 황사 관측. 이 규칙표를 문서로 고정하겠다.
**Cecilia** — 컬러 테스트 프리셋 11종이 공통 모델의 어떤 조합인지 표로 받으면 디자인 토큰 골든 케이스와 1:1로 맞출 수 있다. 기상청엔 없는 조합(예: sky1)이 한국 도시에서 안 나오는 것은 문제없다.
**Lisiena** — 프로토의 `decode2`/`catOf`/`wxLabel`을 그대로 쓰되 입력이 BFF 응답으로 바뀌므로 클라이언트에서 WMO 디코딩을 제거한다. 라벨 문구는 기상청 용어("구름많음")와 프로토 용어("부분 흐림") 중 하나로 통일이 필요하다.
**Lily** — 공통 모델이 확정되면 네이티브 구현은 그 JSON만 소비하면 되어 이식 리스크가 크게 줄어든다.
**Joy** — 매핑 규칙표 자체가 테이블 기반 단위 테스트 대상이다. 기상청 원본 필드 조합 → 공통 모델 → 색상까지 골든 케이스로 검증한다.

**잠정 결론** — 공통 날씨 모델을 BFF 계약으로 확정, 매핑표는 Theo 작성·Cecilia/Lisiena 검토, 라벨 용어는 Mateus가 결정(제안: 기상청 용어 우선).

## 안건 6. 장애·쿼터 소진 정책

**Mateus 제안** — 스테일 캐시는 최대 3시간까지 배지와 함께 표시, 그 이후는 "갱신 지연" 상태. 갱신 우선순위는 실황 > 단기 > 대기질 > 중기 > 해외. 한국 도시는 기상청 장애 시 Open-Meteo로 자동 폴백하되 "대체 데이터" 배지를 붙인다.

**Theo** — 폴백은 소스별 `source` 필드로 응답에 명시한다. 폴백 시 공통 모델은 같으니 화면 변화는 배지뿐이다. 기상청 점검 시간(새벽)에 스케줄이 겹치면 재시도 백오프를 둔다.
**Mark** — 소스별 성공률·지연을 CloudWatch 지표로 두고, 연속 실패 시 알림. 쿼터 소진 시 수집 중단은 자동, 재개는 자정 자동.
**Cecilia** — 스테일·대체·지연·오프라인 네 가지 상태의 시각 언어(배지 위치·색·문구)를 디자인 시스템에 넣는다. 배경색이 날씨를 뜻하므로 "데이터가 오래됐다"는 신호가 배경을 흐리게 하는 식으로 색 자체에 실려도 좋을지 Mateus 판단이 필요하다.
**Lisiena/Lily** — 오프라인은 마지막 BFF 응답을 로컬 저장해 표시하고, 위 네 상태를 상태 머신으로 구현한다.
**Joy** — 각 상태 전이(정상 → 스테일 → 지연 → 오프라인, 폴백 진입/복귀)를 시나리오 테스트로 만든다.

**잠정 결론** — 네 가지 데이터 상태 + 폴백 배지 확정, 배경색으로 스테일을 표현할지는 Mateus·Cecilia 추가 논의.

## 안건 7. 출처 표시와 약관

**Mateus 제안** — 설정 화면 하단 "데이터 출처" 섹션에 기상청(공공누리 1유형), 한국환경공단 에어코리아, 한국천문연구원, Open-Meteo(CC BY 4.0, 링크 포함)를 표기하고, 홈 화면에는 표기하지 않는다.

**Theo** — Open-Meteo는 "Weather data by Open-Meteo.com" 링크 표기가 라이선스 조건이다. 공공데이터는 출처 표시 의무만 있고 위치 규정은 없다. 설정 하단 + 상세 시트 최하단 소형 표기 정도가 안전하다.
**Cecilia** — 홈에 표기하지 않는 것에 동의. 상세 시트 최하단에 10px 텍스트로 넣으면 디자인을 해치지 않는다.
**Joy** — 언어 전환 시 출처 문구도 번역되는지, 링크가 열리는지 체크리스트에 넣는다.

**잠정 결론** — 설정 하단 + 상세 시트 최하단 표기, 문구는 Theo가 라이선스 원문 기준으로 작성.

## 안건 8. 해외 도시 정책

**Mateus 제안** — Open-Meteo 무료 티어로 해외 도시 예보를 1차부터 제공하되, 국가 수를 소수로 제한하고 안건 3의 수요 기반 캐시로 쿼터를 지킨다. 기상청 GTS 관측은 사용하지 않는다.

**Theo** — 해외는 Open-Meteo 단일 소스라 폴백이 없다. 장애 시 스테일 표시로만 대응한다는 점을 기획에 명시해 달라. 국가 확장은 카탈로그에 행을 추가하는 것뿐이라 기술적 비용은 작고, 쿼터가 유일한 제약이다.
**Cecilia** — 해외 도시는 계절 틴트가 열대·남반구에서 어색하다는 리뷰 지적이 그대로 남는다. 1차는 계절 축을 온도 대역 기반으로 단순화하는 안을 제안한다.
**Lisiena** — 도시별 현지 시각 표시가 필요하다(프로토는 `utc_offset_seconds`로 이미 처리). 다중 도시 좌우 스와이프와 시트 상하 스와이프의 제스처 충돌을 설계에서 정리해 달라.
**Lily** — 도시 개수 상한(예: 10개)을 두면 백그라운드 갱신과 배터리 계산이 단순해진다.
**Joy** — 해외 도시 테스트 세트에 영하(모스크바), 열대(싱가포르), 남반구(시드니), 해안(부산·리스본), 황사(베이징)를 고정 포함한다.

**잠정 결론** — 해외 1차 제공, 국가 소수 제한, 즐겨찾기 도시 상한 10개, 계절 축 단순화는 Mateus·Cecilia 결정 사항으로 이관.

Theo: 카탈로그 스키마 + 공통 날씨 모델 + 매핑표 초안, 기상청·에어코리아·천문연 키 발급. Cecilia: 프리셋↔공통 모델 골든 케이스 표, 데이터 상태 4종 시각 언어, 시간별 스트립 포함 상세 시트 와이어. Lisiena: React 버전 API 계층을 BFF 계약 기준으로 분리, 제스처 범위 수정. Lily: 컬러 엔진 스펙 이식 준비, 카탈로그 번들 구조. Joy: 카탈로그 스모크 테스트, 매핑표 테이블 테스트 설계. Mark: 프리티어 기준 BFF·스케줄러·캐시 구성안, 쿼터 알림.
