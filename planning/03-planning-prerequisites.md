# ColorSense 기획 설계 전 확인 사항 — "기상청 API 제공 국가 + 무료 범위" 결정 기준

작성: 2026-09-14 · 결정(Mateus): 1차 런칭 국가 = 기상청 API가 제공하는 국가, 데이터 소스 = 무료 범위 내로 제한

## 0. 먼저 짚을 것 — "기상청 API가 제공하는 국가"는 사실상 한국이다

기상청이 공개하는 API를 확인하면 두 갈래로 나뉜다. **예보**(초단기실황·초단기예보·단기예보·중기예보)는 한국 전역 5km 격자(nx/ny) 또는 행정구역 코드 기준이라 **한국만** 커버한다. **세계기상**은 API허브의 "세계기상" 카테고리가 세계기상통신망(GTS)으로 수신한 전 세계 지상·고층·해양 **관측** 자료를 제공하는 것이지, 해외 도시 예보 API가 아니다. 날씨누리 웹의 "세계날씨" 페이지는 있지만 공개 API로 제공되는 건 확인되지 않았다.

따라서 이 결정은 실질적으로 "**1차 런칭 = 한국 주요 도시, 예보 포함**"이고, 해외 도시는 (a) 관측값만 보여주거나 (b) 2차로 미루거나 (c) 무료 범위의 다른 소스(MET Norway 등)를 섞어야 한다. 프로젝트 목표 문장("각 나라 주요 도시")과 어긋나므로 **로드맵 문장으로 명시**해 두는 편이 좋다. 예: "1차 한국 주요 도시 → 2차 해외 도시(무료 소스 확정 후)".

## 1. 기획 설계 전에 Mateus가 확정해야 할 것

### 1-1. 상업 여부 (가장 먼저)

"무료 범위"의 정의가 소스마다 다르다. 기상청·공공데이터포털은 출처 표시만 하면 상업 이용 가능(공공누리 1유형). 반면 프로토가 쓰는 Open-Meteo 무료 티어는 **비상업 전용**이라, 앱이 광고·유료·회사 서비스면 쓸 수 없다. MET Norway는 CC BY라 상업 가능하나 앱당 20 req/s 제한. 앱스토어 배포·광고·회사 브랜드 노출 여부를 먼저 정해야 어떤 "무료"가 허용되는지 정해진다.

### 1-2. 도시 목록과 격자 매핑

"한국 주요 도시" 기준을 정한다(특별시·광역시·특별자치시도 + 도청 소재지 + 인구 상위 N = 대략 30~100개). 각 도시에 대해 nx/ny 격자 좌표, 중기예보 지역코드(육상 regId, 기온 regId), 대기질 측정소명, 해안 여부(해양 데이터 대상), 영문 표기를 카탈로그로 확정한다. 단기예보는 격자당 값이 다르므로 "도시 대표 지점"을 어디로 잡을지(시청 위치 등) 정책이 필요하다.

### 1-3. 쿼터 예산과 캐시 정책

공공데이터포털 개발계정은 **일 10,000건**, 운영계정도 시작은 10,000건이며 활용사례 등록 후 증량 신청 가능. API허브 일반회원은 **일 20,000건**. 클라이언트 직접 호출은 불가능한 규모이므로 BFF + 도시별 캐시는 전제다. 기상청 발표 시각에 맞춘 스케줄 수집이면 100개 도시 기준 하루 약 6,000건(실황 24 + 초단기 24 + 단기 8 + 중기 2 = 58건/도시)으로 10,000건 안에 들어간다. 이 계산을 Theo가 검증하고, 운영계정 전환·증량 신청 절차와 리드타임을 미리 파악해야 한다.

### 1-4. 필요한 API가 하나가 아니다

프로토는 Open-Meteo 한 곳에서 날씨·해양·대기질·일출몰을 받았지만, 기상청 체계에서는 같은 정보를 만들려면 여러 기관의 API를 조합해야 한다. 현재/시간별/3일 예보는 기상청 단기예보 조회서비스(실황·초단기·단기), 4~10일은 기상청 중기예보 조회서비스(육상 + 기온, 별도 지역코드), 미세먼지·황사는 한국환경공단 에어코리아 대기오염정보 API(측정소 기준) 및 기상청 황사 관측, 파도는 기상청 해양기상 관측(부이) 또는 해양수산부 바다누리, 일출·일몰은 한국천문연구원 출몰시각 API, 위치→도시는 자체 카탈로그 최근접 매칭(외부 역지오코딩 불필요). 키 5~6개, 각각 쿼터·장애·스키마가 다르다. 어떤 항목을 1차 범위에 넣을지(예: 파도는 2차) 정하면 복잡도가 크게 줄어든다.

### 1-5. 날씨 코드 체계 재정의 — 컬러 엔진에 직접 영향

프로토의 컬러 엔진과 라벨은 **WMO weather_code**(0~99)를 입력으로 받는다. 기상청 단기예보는 하늘상태 SKY(1 맑음, 3 구름많음, 4 흐림)와 강수형태 PTY(0 없음, 1 비, 2 비/눈, 3 눈, 4 소나기, 5 빗방울, 6 빗방울눈날림, 7 눈날림)로 나뉘고, 강수 강도는 PCP/SNO(mm/cm) 값으로, 뇌우·안개는 단기예보에 없다(실황·특보·시정 관측으로 보완). 따라서 `decode2`의 입력을 "SKY + PTY + PCP + 특보 + 시정 + PM10"으로 재정의하고, 컬러 테스트 프리셋(맑음/부분흐림/흐림/비/소나기/눈/진눈깨비/안개/뇌우/미세먼지/황사)이 기상청 필드 조합으로 어떻게 재현되는지 매핑표를 Cecilia·Lisiena와 함께 만들어야 한다. 이 매핑표가 없으면 디자인·개발이 각자 다르게 해석한다.

### 1-6. 장애·쿼터 소진 정책

공공 API는 점검·지연이 잦고, 쿼터를 넘기면 그날은 끝이다. 스테일 캐시를 얼마나 오래 보여줄지(예: 최대 3시간, 배지 표시), 소진 시 어떤 항목부터 갱신을 멈출지(우선순위: 실황 > 단기 > 대기질 > 중기 > 해양), 완전 장애 시 화면 정책을 기획에서 정해 둬야 한다.

### 1-7. 출처 표시와 약관

공공누리 1유형 출처 표시 문구·위치, 에어코리아·천문연 등 기관별 표시, 공공데이터 이용약관상 재배포 조건. Cecilia가 배치할 수 있도록 문구를 확정한다.

### 1-8. 해외 도시의 위치

목표 문장을 지키려면 해외 도시 정책이 필요하다. 선택지: (a) 1차는 한국만, 해외는 로드맵. (b) 해외는 기상청 GTS 관측(현재값)만 표시하고 예보 없음을 명시. (c) 비상업이면 Open-Meteo 무료, 상업이면 MET Norway(CC BY, 전지구 Locationforecast)를 해외 전용 무료 소스로 채택. (c)를 고르면 두 소스의 스키마를 하나로 정규화하는 작업이 Theo에게 생긴다.

## 2. 프로토타입에서 바뀌는 것 요약

위치 잡기는 GPS → 카탈로그 최근접 도시로 단순화되고, 서울 폴백은 "도시 선택"으로 바뀐다. 데이터 계층은 Open-Meteo 4개 엔드포인트 → 기상청 계열 5~6개 API + BFF 정규화. 날씨 코드는 WMO → 기상청 SKY/PTY 조합. 시간대는 KST 고정으로 단순해진다. 언어는 한/영 유지(도시 영문명은 카탈로그에서). 파도·황사는 소스 확정 전까지 범위 미정.
