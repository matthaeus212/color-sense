# ColorSense HTML 프로토타입 리뷰 — 목표 대비 갭 및 개선점

작성: 2026-09-14 · 대상: `colorsense.html` (2026-09-08 버전, 현재 `frontend/`와 동일 로직) · 목표: "각 나라 주요 도시의 정확한 날씨를 제공하는, 완성도 높고 아름답게 디자인된 앱"

## 1. 한 줄 총평

프로토타입은 "날씨를 색으로 보여준다"는 핵심 컨셉을 이미 설득력 있게 증명했다. 온도 기반 6스톱 하늘 팔레트에 구름량·강수·안개·뇌우·황사·주야 변조를 얹는 컬러 엔진, 복합 날씨 라벨("흐림 & 비"), 강수 강도를 빗방울 개수로 표현하는 아이콘, 일출·일몰 아치, 컬러 테스트 모드까지 디자인 방향은 충분히 잡혀 있다. 반면 프로젝트 목표의 나머지 절반인 **"각 나라 주요 도시"**와 **"정확한"** 두 축은 아직 손대지 않은 상태다. 현재 앱은 "내 위치 한 곳"만 보여주는 단일 화면이고, 데이터는 클라이언트가 무료 서드파티 API 4곳을 직접 호출하며, 정확도·신선도·오류를 사용자에게 알려주는 장치가 없다. 다음 단계는 컬러 엔진을 더 다듬는 것보다 **도시 모델·데이터 계층·상태 설계**를 세우는 일이다.

## 2. 목표 대비 핵심 갭 (우선순위 순)

### G1. "각 나라 주요 도시" 기능이 전무 — 가장 큰 갭

프로토는 GPS → IP → 서울(하드코딩) 순으로 위치 하나를 잡아 그 지점만 보여준다. 도시 검색, 나라별 주요 도시 탐색, 여러 도시를 좌우 스와이프로 넘기는 다중 도시 뷰, 즐겨찾기/최근 도시, 도시별 현지 시각 표시 같은 것이 전혀 없다. 목표 문장을 그대로 읽으면 이것이 제품의 뼈대인데 현재는 "현재 위치 위젯"에 가깝다. 필요한 정의는 다음과 같다: 어떤 나라를 커버할지(전체 vs 1차 런칭 국가), 나라당 주요 도시 기준(수도 + 인구 상위 N개 등), 도시 카탈로그의 소유자(백엔드가 정적 데이터로 관리하는지, 지오코딩 API에 의존하는지), 도시 이름의 다국어 표기 소스, 사용자가 도시를 추가·삭제·정렬하는 흐름과 그 데이터의 저장 위치(로컬 vs 계정 동기화 — 역할표에 "인증"이 있으니 동기화를 염두에 둔 것으로 보임).

### G2. "정확한 날씨"를 뒷받침하는 장치가 없음

데이터 소스 자체(Open-Meteo)는 무난하지만, 정확도는 소스만으로 결정되지 않는다. 현재 상태에서 눈에 띄는 문제는 아래와 같다.

날씨를 **한 번만** 불러오고 이후 갱신이 없다. 시계는 15초마다 돌지만 온도·날씨 코드·`is_day`는 처음 값 그대로라, 앱을 켜 둔 채 해가 지면 화면은 계속 낮 배경이다. "마지막 갱신 시각"도 표시하지 않아 사용자가 신선도를 판단할 수 없다.

위치 실패 시 **조용히 서울로 폴백**한다. 사용자는 자기 위치라고 믿고 서울 날씨를 본다. 정확성을 표방하는 앱에서는 "위치를 확인할 수 없음 → 도시를 선택하세요"가 맞다.

파도 API가 **실패해도 `null`을 돌려주어 "내륙 · 해당 없음"으로 표기**된다. 네트워크 오류와 실제 내륙을 구분하지 않아 부산에서 오류가 나면 "내륙"으로 보인다. 미세먼지도 실패 시 0(청정)으로 처리되어 오류가 "좋음"으로 둔갑한다.

황사/미세먼지 판정이 PM10 하나에 임의 임계값(≥80 미세먼지, ≥150 황사)을 걸어 놓았다. PM10 고농도는 황사가 아니라 일반 오염일 수도 있고, 한국 기준(PM10 나쁨 >80, 매우나쁨 >150)과 이름만 겹친다. Open-Meteo가 별도로 주는 `dust` 값과 PM2.5를 써서 "황사"와 "미세먼지"를 정의대로 구분해야 하고, 국가별 대기질 지수(AQI/CAI) 기준을 어느 것으로 통일할지 정책이 필요하다.

체감온도(`apparent_temperature`)를 받아오지만 어디에도 표시하지 않고, 시간별 예보는 강수확률만 가져와 현재 시각 한 칸만 쓴다. 오늘 최고/최저, 시간별 온도·강수, UV, 기압, 가시거리 같은 "정확한 정보"의 기본 항목이 없다. 기상 특보(태풍·폭염·한파)도 없다.

역지오코딩(BigDataCloud) 한국어 표기 품질이 도시마다 들쭉날쭉하고, 앱 이름 표기가 서비스 제공자에 종속된다. 도시 카탈로그(G1)를 갖추면 표기는 우리 데이터로 고정할 수 있다.

### G3. 아키텍처 — 클라이언트가 서드파티 API 4곳을 직접 호출

Open-Meteo Forecast/Marine/Air-Quality, ipwho.is, ipapi.co, BigDataCloud를 브라우저가 직접 친다. 키가 없어 편하지만 상용 배포에는 다음 문제가 있다: Open-Meteo 무료 티어는 비상업 용도 한정이며 상업 서비스는 유료 플랜과 키가 필요하다. IP 지오로케이션 무료 API는 호출 제한이 낮고 서비스 중단 이력이 잦다. 응답 스키마가 벤더에 묶여 있어 나중에 소스를 바꾸거나 두 소스를 합성(정확도 향상)할 수 없다. 키를 도입하는 순간 클라이언트에 노출된다. 도시 단위 캐시가 없어 같은 도시를 보는 사용자 수만큼 호출이 늘어난다. 결론적으로 **BFF(백엔드 API)** 가 필요하다: 도시 카탈로그 API, 도시별 날씨 API(정규화 스키마 + 캐시 + 갱신 시각), 검색 API, 즐겨찾기 동기화(인증). 웹·iOS·Android가 같은 스키마를 소비하게 되고, 정확도 개선(소스 교체·합성·보정)이 서버에서만 이루어진다.

### G4. 컬러 엔진을 "스펙"으로 승격해야 앱과 웹이 같은 색을 낸다

컬러 엔진이 JS 함수 안에만 존재한다. Lily가 iOS/Android/Flutter로 만들 때 이 로직을 눈대중으로 옮기면 플랫폼마다 색이 어긋난다. 앵커 팔레트(`ANCHORS`, `SKYPOS`, 계절 대표색), 변조 규칙(구름량 mute/dk, 강수, 안개, 뇌우, 황사, 야간 계수)을 **JSON + 알고리즘 문서**로 분리하고, 입력(온도·wx·계절·주야) → 출력(6스톱 RGB) 골든 테스트 케이스 표를 함께 만들어야 한다. 이 표는 Joy의 시각 회귀 테스트 기준이자 Cecilia의 디자인 시스템 토큰이 된다.

엔진 자체의 개선점도 있다. `buildStops`가 온도를 0~36°C로 클램프해 **영하는 전부 0°C와 같은 색**이다(모스크바 −15°와 서울 0°가 동일). 팔레트 `TOP/BOT`는 −10°C까지 정의돼 있지만 하늘 배경에는 쓰이지 않고 주간 예보 막대에만 쓰인다. 계절 틴트는 월 기반(남반구 6개월 시프트)이라 열대·적도 도시는 "봄/여름"만 반복되며 의미가 약하다 — 글로벌 도시가 목표면 계절 축을 위도·기후대 기반으로 재정의하거나, 계절 대신 "체감 온도 대역"으로 단순화하는 결정이 필요하다.

### G5. 디자인 완성도 — 좋은 출발, 아직 "폴리시"는 아님

가독성: 고온(30° 이상) 주간 팔레트는 하단이 밝은 살구·주황이라 흰 텍스트 대비가 낮다. 온도 78px 글자는 괜찮지만 도시명·좌표·시트 안 작은 텍스트(9~10.5px, opacity .55~.65)는 WCAG AA에 못 미칠 가능성이 높다. 배경이 동적이므로 텍스트 뒤 그라데이션 스크림 또는 배경 밝기에 따른 텍스트 색 자동 전환 규칙이 필요하다.

타이포그래피가 시스템 폰트 폴백(Helvetica Neue → Apple SD Gothic Neo → …)에 의존하고 한글에 6px 자간을 주어 "S E O U L"과 "서 울"의 리듬이 다르다. 디자인 시스템에서 한글/영문 각각의 서체·자간·웨이트를 정해야 한다.

모션: 빗방울 최대 56개 + 눈 48개 + 구름 3개 + 황사 30개 DOM 요소가 각각 무한 애니메이션을 돌린다. 저사양 기기 배터리와 프레임 문제가 예상되며 `prefers-reduced-motion` 대응이 없다. 앱에서는 캔버스/셰이더 또는 파티클 수 상한이 필요하다.

정보 구조: 홈은 현재 상태만, 상세 시트는 4개 타일 + 주간 7일뿐이다. 시간별 예보 스트립, 오늘 최고/최저, 체감온도, 일출·일몰 외 달 위상 같은 확장 영역이 비어 있다. "설정" 안의 컬러 테스트는 개발·QA용 도구인데 사용자 설정과 같은 위치에 있다 — 숨김 디버그 메뉴로 분리해야 한다. 단위(°C/°F, m/s·km/h·mph), 시간 형식(12/24h)이 설정에 없다.

### G6. 상호작용 버그 및 상태 처리

스와이프 감지가 화면 전체 `pointerdown` 기준이라 **상세 시트 안 주간 예보 목록을 위로 스크롤(손가락을 아래로)하면 시트가 닫힌다.** 설정 패널이 열린 상태에서도 스와이프가 시트를 열고, 슬라이더를 드래그해도 같은 문제가 생길 수 있다. 제스처는 핸들 영역·시트 헤더로 한정하고 스크롤 컨테이너에서는 무시해야 한다.

로딩·오류 상태가 한 종류("불러오지 못했어요 / 다시 시도")뿐이다. 위치 권한 거부, 오프라인, 부분 실패(날씨는 왔지만 대기질 실패), 타임아웃, 캐시된 값 표시(스테일 배지)가 각각 구분되어야 한다.

`S.storm` 변수는 어디서도 설정되지 않는 죽은 코드이고, 언어 전환 시 `render()` 전체가 다시 돌아 대기 효과가 전부 재생성되며 애니메이션이 튄다.

### G7. 다국어·지역화 범위

현재 ko/en 두 언어, 섭씨 고정, 12시간제 고정, 날짜 "9월 14일 / SEP 14" 고정이다. 각 나라 주요 도시가 목표라면 최소한 단위·시간·날짜 형식은 로케일별 분기가 필요하고, 언어 확장을 전제로 i18n 키 구조를 지금 정리해 두는 편이 싸다. 도시명 다국어는 G1의 카탈로그에서 해결한다.

### G8. 품질·운영 기반 부재

테스트 코드가 없다(컬러 엔진 단위 테스트, WMO 디코딩, 라벨 조합). 접근성 속성(aria-label, role, 포커스 순서)이 없다. 모니터링·에러 리포팅·분석 이벤트가 없다. 배포는 정적 파일이면 되지만 BFF가 생기면 캐시·레이트리밋·서드파티 장애 알림이 필요하다.
